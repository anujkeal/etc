# ETC — Four-Week YouTube Launch Plan

## The goal

For the first four weeks, publish **one well-researched main video each week**, supported by two short videos made from the same research.

ETC will explore complex technology, but explain it in plain, precise language. We are not trying to make the subject look complicated. We are trying to make the complicated subject understandable.

**The rule for every episode:** one central question, one clear story, simple explanations, and real examples.

## Our presentation style

- Use everyday English. Introduce technical terms only when they are useful, then explain them immediately.
- Explain one idea at a time. Do not overload the viewer with definitions.
- Use familiar comparisons to introduce an idea, but explain where the comparison stops being accurate.
- Show the process with diagrams, animations, screen recordings, or small demonstrations.
- Keep the narration natural, curious, and confident—not like a classroom lecture.
- Use a clean visual style: uncluttered frames, readable text, consistent typography, and only graphics that help explain the subject.
- Avoid clickbait, exaggerated claims, unnecessary jargon, and complicated titles.
- Be honest about what is known, what is simplified, and what is uncertain.

## Week 1 — What Actually Happens When You Open a Website?

**Working title:** What Actually Happens When You Open a Website?

**Central question:** When you type a website address and press Enter, what happens between your device and the website appearing on your screen?

**Why this is our first episode:** It starts with an action almost everyone understands and reveals the hidden systems behind it.

**Story outline:**
1. Start with the familiar action: type a website address and press Enter.
2. Explain that the browser needs to find the computer serving that website.
3. Introduce DNS as a system that helps find the address associated with a domain name.
4. Explain, at a beginner-friendly level, how the browser connects to a server.
5. Introduce the request and response: the browser asks for resources and the server sends them back.
6. Show how the browser turns those resources into the page we see.
7. End with the idea that a simple click can involve many computers and systems working together.

**Visuals and demonstration:**
- Record a browser opening a website.
- Animate the journey: browser → DNS lookup → server → response → rendered page.
- Use a simple diagram to distinguish a domain name, IP address, browser, and server.
- Avoid presenting DNS as the entire internet; it is one part of the process.

**Shorts:**
- What is DNS, in under a minute?
- What does a web server actually do?

## Week 2 — How Does Code Become a Running Program?

**Working title:** How Does Code Become a Running Program?

**Central question:** A programmer writes text on a screen. How does that text turn into actions performed by a computer?

**Story outline:**
1. Show a tiny program and ask how a computer can understand it.
2. Explain that humans write instructions in programming languages.
3. Introduce the idea that processors operate using machine-level instructions.
4. Explain the role of a compiler or interpreter, carefully distinguishing their jobs.
5. Follow a small example from source code to execution.
6. Explain that the CPU executes instructions while memory holds data and instructions needed during execution.
7. End by showing that code is not magic: it passes through layers of software and hardware.

**Visuals and demonstration:**
- Show a short, original Python program.
- Use a simple flow diagram: source code → language implementation/runtime → machine instructions → CPU execution.
- Explain that different languages and runtimes work differently; do not imply every language follows one identical path.

**Shorts:**
- What is a compiler?
- What does the CPU do when a program runs?

## Week 3 — Why Do Programming Languages Exist?

**Working title:** Why Do We Have So Many Programming Languages?

**Central question:** If computers ultimately work with machine instructions, why do programmers use so many different languages?

**Story outline:**
1. Begin with the problem of writing instructions directly in machine code.
2. Introduce assembly language as a more readable way to represent low-level instructions.
3. Explain the move toward higher-level languages that let people express ideas more conveniently.
4. Show how languages make different trade-offs: control, readability, performance, safety, ecosystem, and ease of development.
5. Compare a tiny task in two languages, such as Python and C, without declaring one universally better.
6. Explain that languages are tools shaped by the problems people want to solve.
7. End with the question: what makes a language suitable for a particular job?

**Visuals and demonstration:**
- Show a simple task written in Python and C.
- Use a visual ladder: machine code → assembly → higher-level languages.
- Explain that this is a simplified way to understand levels of abstraction, not a complete history of every language.

**Shorts:**
- What is machine code?
- Why was Python designed to be readable?

## Week 4 — How Did the Internet Begin?

**Working title:** How Did the Internet Begin?

**Central question:** How did researchers connect separate computers into a network that eventually became the global internet?

**Story outline:**
1. Start with the modern internet and ask how it began.
2. Set the historical context: researchers needed computers at different locations to communicate and share resources.
3. Introduce ARPANET as an important early network—not the internet in its complete modern form.
4. Explain packet switching with a simple, carefully qualified analogy: information is divided into packets that can travel through a network.
5. Introduce the development and adoption of TCP/IP as a key step in connecting different networks.
6. Distinguish the internet (the network infrastructure) from the World Wide Web (a service built on top of it).
7. End by connecting those early research networks to the systems people use today.

**Visuals and demonstration:**
- Use a simple timeline of major milestones.
- Animate a message being split into packets and reassembled.
- Show the distinction between the internet and the Web with a clean diagram.
- Verify historical dates and claims against reliable sources before recording.

**Shorts:**
- What was ARPANET?
- What is the difference between the internet and the World Wide Web?

## Weekly production routine

| Day | Work |
|---|---|
| Monday | Choose the episode's central question; research reliable sources. |
| Tuesday | Build the outline and verify technical and historical claims. |
| Wednesday | Write and revise the narration script. |
| Thursday | Prepare diagrams, demonstrations, screen recordings, and visuals. |
| Friday | Record narration and assemble the first edit. |
| Saturday | Edit, fact-check the finished video, and prepare the thumbnail and description. |
| Sunday | Publish the main video; prepare or schedule the two Shorts. |

This is a target workflow, not a reason to publish an inaccurate or unfinished video. If research or editing takes longer, quality takes priority over the calendar.

## A clean topic checklist

Before approving any topic, answer these questions:

1. Can we express the episode in one clear question?
2. Can a viewer understand why the question matters?
3. Can we explain the core idea without assuming specialist knowledge?
4. Can we demonstrate or visualise at least one important part?
5. Can we verify the important claims using trustworthy sources?
6. Does this topic offer something distinct from our other episodes?

If the topic needs five unrelated questions to explain it, narrow it. If a technical term does not help the viewer understand the story, remove it.

## Research and accuracy standard

For each episode, keep a source list. Prefer original papers, official technical documentation, standards, historical archives, books from reputable publishers, and credible reporting. Check dates, names, quotations, and technical claims. Never invent a quotation, experiment, source, or historical detail.

A simple explanation must remain accurate. Analogies are teaching tools—not substitutes for explaining how something really works.

## What success means after four weeks

At the end of this first cycle, review:
- Whether viewers understand the main idea.
- Audience retention and where viewers leave.
- Comments and questions that reveal confusion.
- Which topics and visual explanations generate genuine interest.
- How long research, scripting, and editing actually take.

Use that evidence to improve the next four episodes. The first month is a learning cycle, not a race for views.
